E2E Eval Runs

Running, viewing, and managing remote workflow eval runs from the forge console.

Overview

The E2E tab in the forge console surfaces live results from the forge eval suite. Each run exercises the full workflow stack — model calls, MCP tool calls, assertion evaluation — against a real dorinda-prod surface and records per-workflow verdicts, timing, token spend, and integrity class.

Runs are stored in the forge control-plane results database (CONSOLE_CP_DB_URL). The tab shows the last 100 runs, newest first, with a sparkline of the pass-rate trend across the 10 most recent.

Triggering a run

Click ▶ Run to open the run dialog, or ↻ Re-run… on any workflow row to open it pre-filled with that workflow. The dialog asks for the provider first, because the provider decides which workflows can run at all.

Step 1 · Provider

Tick openai, anthropic, or both. A banner then states how many workflows the selection excludes, and why. In the current catalogue 10 are pinned to openai (they assert host-native ChatGPT behaviour) and 3 are cross-host — those need both providers selected and run as a single spanning execution.

Step 2 · Scope

Six presets cover the common intents:

  • Full catalogue — everything the selected provider can run.
  • Critical / Release gate — the named suites.
  • Last run's rejections / Last run's withheld — sourced from the most recent run's actual rows. This is the normal triage path.
  • Choose… — the whole catalogue as a filterable checkbox list, grouped by id family, with per-group Select all.

A workflow the provider selection cannot run is shown struck through with an openai only or needs both tag and its checkbox is disabled. If a preset includes one it is excluded by name rather than silently dropped, and the spend estimate counts only what will really run.

Why you can no longer type workflow ids. The results table displays row ids such as W-001:blocked — the workflow id joined to its plan label. On 2026-08-16 one was pasted into the old free-text field; the runner found no matching workflow file, exited 2, and the whole run died in 16 seconds having executed nothing. Ids are now chosen from the catalogue, the label is stripped wherever a stored row becomes a run target, and the API answers 400 unknown_workflows naming the offending ids rather than spending a job execution on a selection that cannot run.

The catalogue is published by forge-hat on every run (it already reads suites/full.yaml), so a one-workflow verification run refreshes the picker exactly as a full run does. If no run has ever published one, the dialog falls back to the text field and says so — an empty picker and an empty catalogue must not look alike.

A reason (minimum 3 characters) is required — it is written into the audit log and stored in the run's metadata so that runs triggered at 3 am have a traceable rationale.

Triggering starts a Cloud Run Job execution (CONSOLE_E2E_JOB) and pre-creates the run row in the results store so the tab shows progress immediately. The run transitions from running to completed, failed, or aborted when the runner publishes its final result.

Cost notice: every eval run makes real LLM calls and costs real money. Confirm the cost checkbox in the modal before submitting. Full-suite runs currently cost roughly $2–5 USD; smoke runs are substantially cheaper. Check the Spend column on the run history list after the run completes.

Reading results

Click any row on the run history list to open the run detail view. The 7 metric tiles at the top act as filters:

AttemptedTotal workflows the runner started (filter: all).
AcceptedWorkflows where the judge returned pass.
FailedWorkflows with verdict fail — the product failed a bar.

Deleting a run

Each row on the run history list has a ✕ delete control on the right. Activating it opens a confirmation dialog that shows the run ID and its start time. Deletion requires an explicit confirmation click.

Deletion is irreversible. Deleting a run permanently removes the run record and ALL child data: per-workflow drilldown rows, scene assertions, MCP call logs, and extracted claims. There is no undo, no soft-delete, and no export step. If you want to preserve the data, export the cassette from the workflow drilldown panel first.

Deletion rules:

  • A run whose status is running cannot be deleted. Stop the Cloud Run execution or wait for it to finish, then delete.
  • Only operators with an active OIDC session can delete runs. The read-only automation token is refused.
  • The delete is atomic — child records (workflows, scenes, MCP calls, claims) are removed in the same database transaction via ON DELETE CASCADE foreign keys. No orphaned rows can survive to be counted by a metric.
  • An audit record (operator identity + timestamp + outcome) is written before the delete is attempted, so the action is recorded even if the database call fails mid-flight.

Permalink to a deleted run

If you open a direct link to a run that has been deleted (e.g. from a Slack message or a previously shared URL), the console shows a clear "This run was deleted" banner rather than a loading spinner or an empty shell. No data is shown because no data exists.

REST endpoint

The delete is exposed as:

DELETE /api/e2e/runs/:run_id
StatusMeaning
200{"deleted": true, "run_id": "..."} — run and all children removed.
404Run not found (never existed, or already deleted).
409Run is currently running — stop or let it finish first.
401Not authenticated.
403Authenticated as read-only (automation token) — not permitted.
501Results store not configured (CONSOLE_CP_DB_URL unset).

Authorization is via the same OIDC session cookie as all other console write operations. No new IAM permissions are required; the endpoint uses the same CONSOLE_CP_DB_URL Postgres connection pool as POST /api/e2e/runs.

Triage protocol (agent use)

When using Claude or an AI agent via the MCP surface, the mandatory triage sequence is:

  1. list_e2e_runs — orient: see the trend, find the failing run, locate a clean baseline.
  2. diff_e2e_runs — compare against the last clean run to isolate regressions from pre-existing failures.
  3. get_e2e_run — read the top-line: pass_rate, withheld_count, rejected_count, integrity.
  4. get_workflow_result — for each failing workflow: read integrity_class BEFORE drawing conclusions.
Never treat a single run as conclusive. diff_e2e_runs confirms a regression; a one-off failure is noise until confirmed across multiple runs. A corrupted integrity class means an infrastructure failure — do not file a product bug until a clean run reproduces the failure.

The MCP surface is read-only — no MCP tool can trigger or delete runs. Triggering and deleting are operator actions available only via the console UI or authenticated REST calls.
