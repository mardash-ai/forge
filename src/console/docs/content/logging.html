Logs, owners & traces

The console's Explore tab — how a support question becomes a filter instead of a text search, and what the Trace pivot actually returns.

The question this surface exists to answer

Someone contacts support. The first move is “show me everything that happened to this user” — filter by their email, then by level, and look for the smoking gun. That only works if every line names who it was for, in the same field, every time. Grepping message text finds the line you already had and none of the ones around it.

Filter by email, not by owner id. The dropdown resolves email → owner at query time from the account list. The logs themselves never contain an address — see Why logs never contain an email.

The envelope every line carries

Lines are written through src/platform/logger.ts, which stamps a fixed envelope. The service needs no field — Cloud Run stamps resource.labels.service_name on every entry automatically.

FieldMeaningWhere it comes from
severityDEBUG · INFO · WARNING · ERROR · CRITICALthe call. Cloud Logging promotes it to the entry's own level, which is what makes the level filter work at all
typewhat happened — mcp.dispatch, gcal.writeback.failedthe call
ownerwhose work this wasthe request context, never the caller
trace_id32-hex id joining every line of one requestthe W3C traceparent
opthe route or job that started the workthe request context

owner is always present and explicitly null when the work belongs to nobody — cron, webhooks, health probes. A missing key would mean “we didn't know”, and those are different answers to the question you are asking.

A caller cannot set owner itself. The logger rejects it as a reserved field. If a call site could attribute its own line, one wrong call would make the filter confidently return someone else's data — which is worse than having no owner at all, because you would believe it.

What the Trace button returns

Every line emitted while handling one request carries the same trace_id, so the pivot returns the whole request: the inbound line, the authenticated request, the MCP dispatch, the gate decision, the calendar write-back, and whatever Google said about it.

Two lines are the floor, not the ceiling

Both come from different runtimes, on purpose:

  • http.request — from the edge middleware. It mints the traceparent when the caller supplies none. It can never carry an owner: the edge runs before auth and has no AsyncLocalStorage.
  • request.authenticated — from the Node runtime, at the single point every authenticated request passes. Same trace id, plus the owner and op the edge could not know.
Why the second one exists. Without it a successful request produced exactly one entry in the whole system, so a trace pivot returned the line you already had. It is emitted at auth rather than at response because Next has no per-request completion hook short of wrapping all 89 route files — and the ones that got forgotten would be silently invisible. The trade: it reports the request starting. The outcome lines carry the status.
One id, one name. A route emitting its own correlation field splits a trace in half and nothing fails — the pivot just quietly returns a subset. /api/mcp/handler did exactly this, logging the full traceparent under correlation_id while everything else logged the 32-hex id under trace_id, so pivots into the busiest path in the product matched zero times. A guard test in tests/logging-consistency.test.ts now fails if any route reintroduces a second name.

Sweeps: attribution is per ITEM, never per sweep

Cron sweeps have no ambient owner — but they know exactly whose work each item is. The reminder, event-alert, routine, delegation-overdue, calendar-sync and proactive sweeps each set the context inside the loop, so “why didn't I get notified?” is answerable by filter.

The sweep summary stays owner: null, which is honest: the scheduler asked for it, not a user. Setting the context once at the top of a sweep would stamp every line with whoever happened to be first — worse than no owner, for the same reason as above.

Why logs never contain an email

Cloud Logging retains entries outside the app's database, so an address written into a line survives the account it belongs to. A purge structurally cannot reach it. That would be a self-inflicted version of the exact failure the tenant teardown exists to prevent.

This is enforced, not documented. The logger drops PII-shaped field names outright and redacts anything address-shaped in a value — because otherwise the field just gets called contact or to next time. An owner id is opaque; once the account is gone it refers to nobody.

The one file still writing to console directly

src/platform/observability/index.ts is vendored from forge and marked do not hand-edit. Converting it in the consumer would be reverted by the next re-vendor, so it stays exempt and the durable fix is forge-side: the observability client should take a host-supplied log sink. Its three lines already emit severity and type, and an OTLP export failure belongs to no user — so the only missing field is one that would have been null.

Everything else goes through the logger, held there by a ratchet test that fails both when a new file calls console.* and when an exempt file has been cleaned up and left in the list — so the exemption list cannot rot in either direction.
