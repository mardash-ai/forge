CI/CD — how everything ships

Two planes, one rule: humans merge; CI ships. Infra changes apply via forge infra in CI; code reaches Cloud Run only via the release pipelines. Local applies are spent (§3.8) and local releases are retired.

🧾 Honesty note: during cutover night (2026-07-30) the FIRST images were rolled from a laptop under time pressure — the release pipelines didn't exist yet. That gap is now closed: all five services have release.yml, and the laptop path is dead (expired ADC, and nothing left that needs it).

Where the release actually happens

A fair question about the diagrams below: every lane ends in a check, never in a "ship" box. That is deliberate, and it is the single most important thing to understand about this pipeline.

📌 Read it this way. Blue lanes ship no code at all — infra.yml's deliverable is converged infrastructure, so a behaviour check is its natural end. Green lanes ship code, and the release is box 3 (release-image, where traffic moves); box 4 is the proof it landed. Ending at "release" would be exactly the false-green this system exists to prevent — we hit it live: gcloud run services update exited 0, the config updated, the container failed to import, and the old revision kept serving.
⚠️ The honest limitation. The gate runs after the change lands. A red gate does not roll back — it tells you fast. Recovery is a human running release-image with the previous digest (see Runbooks).

The probe that would have caught the cutover

/api/health is dependency-free on purpose — it reports process liveness, so it returns 200 while every upstream is broken. /api/health/deep is its opposite, and it is what the api's release gate asserts:

CheckCatches
databaseCloud SQL unreachable from the VPC
data_planethe forge sidecar down or unroutable
data_plane_app_callbackthe cutover's worst bug — the data-plane calling back to a local address, so every handler dies while both health probes stay green
external_egressthe missing Cloud NAT — Stripe and SMTP hanging while the service looks perfect
🧭 The rule going forward: when a release ships a failure this endpoint would not have caught, the fix includes a new check here. Otherwise the gate only ever catches the bugs we already know about.

Every workflow, explained

One card per workflow: what it exists for, when it fires on its own, when you run it, and what green/red actually mean. Grouped by repo.

In every service repo — infra.yml the only way infrastructure changes

What it's for: applying that repo's declared stack (its infra/*.tf + forge.infra.json) to GCP via forge infra. The repo you're in is the stack it manages — shared-infra's manages the VPC/LB/DNS/certs; a service repo's manages its Cloud Run service, secrets containers, backend.

Fires on its own: ① PRs touching infra/** → runs lint + plan only (read-only — the plan is your review artifact). ② Merges touching those paths → apply (with the re-plan-until-empty read-back) then verify (the repo's declared behavior checks — a red verify fails the run). ③ Nightly at 06:17 UTC → the drift gate: status exits 2 if GCP no longer matches git.

Run it by hand when: you want an on-demand drift check (dispatch = plan only, safe), or after fixing an external blocker (e.g. a secret value was missing) — "Re-run failed jobs" resumes exactly where it died; applies are idempotent.

Green: declared == applied == verified-working. Red on a merge: the apply or verify failed — read the last step's log; it names the resource. Red on the schedule: DRIFT — someone/something changed GCP outside git. That's the alarm working; the log shows the exact diff.

Special case — dorinda-ci-runners' copy runs on GitHub-hosted runners: the stack that manages the self-hosted pool must never depend on the pool it manages.

site · web · api · devs — release.yml the only way code ships

What it's for: moving code (a container image) onto the already-provisioned Cloud Run service. Build on the in-VPC runner → push to Artifact Registry → forge infra release-image: digest-pinned, then waits for the new revision to go Ready and re-reads the served image. Infra deliberately ignores image changes — this pipeline is the code plane.

Fires on its own: merges to main touching app paths (each repo's list is in its YAML — e.g. api: app/src/**, app/migrations/**; devs: site/**, server.mjs).

Run it by hand when: you need a redeploy with no code change (config/secret value changed — Cloud Run resolves secret latest at revision creation, so a new revision is what picks it up), or a previous run died on a Spot preemption.

Green: the LAST log line reads release: <svc> → <image@sha256:…> (revision Ready ✓) — that read-back is the proof; without it, nothing shipped. Red: build failure (readable), or "revision NOT ready" — the new image boots broken and traffic stays on the previous revision (Cloud Run keeps serving last-Ready; a red release never takes prod down).

dorinda-api — ci.yml quality gates

What it's for: the merge-quality bar: typecheck, the offline test suite (DB-gated tests self-skip), the MCP contract check (tool surface vs contract/mcp-tools.json — drift here is a safety bug), and the npm-audit gate — ASVS V14, the CASA-critical control. Known findings are accepted via expiring exceptions (scripts/audit-gate.mjs): next@14's HIGHs expire 2026-09-01, at which point the build goes red until the Next 16 migration lands.

Fires on its own: every push and PR — no path filter, it's cheap and always relevant. Runs on GitHub-hosted runners (needs no GCP).

Run it by hand when: never needed — push and it runs. Red: a genuine test/type/contract failure, a NEW high/critical CVE, or an expired exception. Don't weaken the gate; fix or consciously extend the exception in a reviewed commit.

dorinda-api — db-migrate.yml manual only, deliberately

What it's for: applying app/migrations/*.sql to Cloud SQL from inside the VPC — the private-IP database is unreachable from anywhere else, including your laptop. Reads DATABASE_URL from Secret Manager at run time.

Run it when: a merge added a migration file, BEFORE dispatching/letting the api release roll (schema first, then code). Caution: the runner is minimal (no tracking table yet) — re-running already-applied migrations errors on CREATE; that error is noisy but harmless. A tracked runner is on the hardening list, after which this step folds into the api release pipeline automatically.

site · web · api — publish.yml LEGACY — the box era

What it was for: the pre-GCP path — multi-arch image builds pushed to GHCR for the Mac's compose stack (fast-deploy-* / forge release on the box). Manual-dispatch only since 2026-07-20 (it was the top Actions-minutes consumer).

Run it when: don't. It still works and stays until the box is decommissioned (it's part of the rollback story), then gets deleted with the rest of the box tooling (Phase 5).

forge — ci.yml + image-smoke.yml platform quality

What they're for: forge's own bar. ci.yml: unit tests + typecheck, then the same suite again against a real Postgres + MinIO ("green on both backends" is enforced, not claimed). image-smoke.yml: boots the built images and probes them.

Fire on their own: every PR and push to main (forge is public — Actions is free and unmetered here). Run by hand: not needed.

forge — publish-image.yml + publish-data-plane.yml platform releases

What they're for: publishing the forge control-plane and data-plane images to GHCR when a version tag (vX.Y.Z) is pushed — the release half of forge's release-then-adopt discipline. Consumers then adopt by bumping a pinned ref/digest in a reviewed commit.

Fire on their own: tag pushes (that's what "forge 0.79.x was released 17 times on cutover night" actually did). Run by hand when: a tag build flaked. Note: these publish arm64 (the box's architecture); the GCP data-plane image was rebuilt amd64 from the pinned tag — adding multi-arch here is on the hardening list.
