### forge-eval-runner database detail

- **Database:** `cp_results`
- **User:** `app` (password generated by Terraform, stored in Secret Manager — see secrets table)
- **Private IP only** — no public address; Cloud Run Job connects via Direct VPC Egress
- **PSA peering** must exist on the VPC (established by the `network` module's `google_service_networking_connection.psa`)
- **Backups + PITR** enabled (7-day retention)
- **Autoresize** enabled — disk grows on demand; does not shrink

### Triggering the eval runner job

```sh
gcloud run jobs execute forge-eval-runner \
  --region <region> \
  --project dorinda-prod \
  --args "eval,<suite-file>,--app,<app-name>,--mcp-url,<mcp-url>"
```

The job template defines the container and secrets; suite-specific args are passed at invocation
time via `--args`. Job logs are available in Cloud Logging under the `cloud_run_job` resource.

## Secret Manager secrets

> **Convention.** Terraform creates the SECRET CONTAINER. The secret VALUE is added out-of-band
> by the operator unless explicitly noted "TF-seeded" — that value is never stored in git or in
> plaintext. The standard command to add a value:
>
> ```sh
> printf '%s' '<value>' | gcloud secrets versions add <secret_id> \
>   --project dorinda-prod --data-file=-
> ```

### GitHub Actions runner

| Secret ID | Seeded by | Value | Purpose |
|---|---|---|---|
| `github-runner-pat` | Operator (OOB) | GitHub PAT with `admin:org` scope | CI runner registers at the GitHub org level on boot. Rotate: update the secret version, then replace the MIG instance. |

### Product services (per-service pattern)

Product service secrets are declared in the `service` module via `secret_env` / `secret_files`.
Each service's secrets are prefixed with the service name (e.g. `dorinda-api-*`). Their SAs are
granted `secretAccessor` on their own secrets only. See the `dorinda-api` infra runbook for the
complete list.

### forge eval runner — **NEW (2026-08-11)**

| Secret ID | Seeded by | Value | Purpose |
|---|---|---|---|
| `forge-eval-runner-db-password` | **TF-seeded** (random_password) | 32-char hex password for the `app` user on `forge-eval-runner` Cloud SQL | Stored for break-glass / rotation reference. Not read directly by the job (the job reads `forge-eval-runner-db-url`). |
| `forge-eval-runner-db-url` | **TF-seeded** (composed from instance private IP + password) | `postgresql://app:<pw>@<private-ip>:5432/cp_results` | `FORGE_DB_URL` — the cp-results Postgres connection string. Wired into the Cloud Run Job template. |
| `forge-eval-runner-anthropic-key` | Operator (OOB) | Anthropic API key | `ANTHROPIC_API_KEY` — eval runs Claude as both the agent-under-test and the LLM judge. Obtain from `console.anthropic.com`. |
| `forge-eval-runner-openai-key` | Operator (OOB) | OpenAI API key | `OPENAI_API_KEY` — eval runs GPT as the second agent-under-test. Obtain from `platform.openai.com`. |
| `forge-eval-runner-service-token` | Operator (OOB) | Random 32-byte hex token | `AUTH_SERVICE_TOKEN` — the eval runner mints MCP access tokens for the target app via `POST /oauth/admin/token`. Must match the `AUTH_SERVICE_TOKEN` configured in the target app's forge data-plane. |

#### Setting out-of-band secrets after first apply

```sh
# Anthropic API key
printf '%s' 'sk-ant-...' | gcloud secrets versions add forge-eval-runner-anthropic-key \
  --project dorinda-prod --data-file=-

# OpenAI API key
printf '%s' 'sk-...' | gcloud secrets versions add forge-eval-runner-openai-key \
  --project dorinda-prod --data-file=-

# Service token (must match the target app's AUTH_SERVICE_TOKEN)
printf '%s' "$(openssl rand -hex 32)" | gcloud secrets versions add forge-eval-runner-service-token \
  --project dorinda-prod --data-file=-
```

#### Rotating the database password

The db-password and db-url secrets are Terraform-managed. To rotate:
1. `terraform apply` with a `random_password` replacement taint (or change a keeper).
2. Terraform will create new secret versions for both `*-db-password` and `*-db-url`.
3. Restart any running jobs (in-flight jobs reading the old `latest` version will finish; new invocations pick up the new URL automatically because the job reads `version = "latest"`).

## Apply gate

**No resource in this file is applied without Mark's explicit go at `terraform apply` time.** The
workflow is:

1. `forge infra plan --env prod` — presents the plan for review.
2. Mark approves the plan in the terminal.
3. `forge infra apply --env prod` — applies, then re-plans to confirm empty diff (§3.7 read-back).

The `forge-eval-runner` Cloud SQL instance (~$10–15/mo billed from first apply) and the Cloud Run
Job (billed per execution, ~$0 at rest) were architecture-approved 2026-08-11. Apply-time
approval is still required per this file's policy.
